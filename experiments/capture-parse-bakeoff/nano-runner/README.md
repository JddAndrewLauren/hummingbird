# nano-runner — the on-device half of the capture-parse bake-off

A phone-only Android app that runs all 42 captures in `../corpus.jsonl` through
**Gemini Nano (nano-v3, ML Kit GenAI Prompt API)** in airplane mode and writes
`nano_results.jsonl` in the same shape as `../hosted_results.jsonl`.

It exists so Phase 3 of `../RUNBOOK.md` collapses to: install → download the model on
Wi-Fi → airplane mode → tap Start → share three files.

---

## Operator runbook (Pixel 10 Pro Fold)

1. **Install** the APK (sideload is fine):

       adb install -r app/build/outputs/apk/debug/app-debug.apk

2. **Open the app on Wi-Fi.** If it says *Model download needed*, tap the button and let
   it finish. This is the only step that touches the network — AICore provisioning
   cannot happen offline.
3. **Airplane mode ON, Wi-Fi off.** Leave it that way for the whole run. Offline-ness is
   the claim under test, and the app records the system's airplane-mode flag at run start
   so the evidence is sampled rather than asserted.
4. **Tap Start.** The screen shows `n / 42` and an error count, nothing else — see
   *Blindness* below. Keep it awake (the app holds the screen on); the run is attended.
   If you leave and come back, finished captures are never re-run.
5. **Tap Share** when it's done and send yourself all three files:
   - `nano_results.jsonl` — the results (this is the one the merge script reads)
   - `nano_raw.jsonl` — verbatim model output + latency per capture (audit sidecar)
   - `nano_run_meta.json` — device, ML Kit version, generation config, airplane flag, counts

   Or pull them over USB:

       adb pull /sdcard/Android/data/net.twinion.nanorunner/files/ ./nano-out

6. **Drop `nano_results.jsonl` next to the harness** (`experiments/capture-parse-bakeoff/`)
   and run:

       ./merge_nano.py            # or --check first

   That validates every parse against `schema.json`, classifies the failures, fills the
   `nano` column of `scoring.md`, and prints a summary you can paste into
   [#42](https://github.com/JddAndrewLauren/hummingbird/issues/42).

### If a capture fails

Let it. An API error, a fenced answer, prose around the JSON — each is recorded as that
row's result and never retried. "How often does on-device inference fail, and how" is one
of the questions the bake-off is asking; a retry loop would quietly answer it wrong.

---

## Blindness

The screen never shows a parse, an error message from the model, or raw output — only
state, `n / 42`, an error **count**, the failing **ids**, and the harness commit. The
blind ground-truth labelling (Phase 2) may still be outstanding when the run happens, and
seeing model output first would anchor the labels. This is a hard requirement, not a
styling choice; if you touch the UI, keep it true.

---

## What it does, and the one invariant

For each capture, the app assembles the prompt **exactly** as `run_hosted.py
--emit-prompts` does:

```python
prompt = template.replace("{{SCHEMA}}", schema_text.rstrip()).replace("{{RAW}}", raw)
```

— the whole of `prompt.md` as the template, `schema.json` trailing-trimmed, the raw
capture verbatim, in that order. Identical prompts on both sides is what makes the
bake-off a comparison of models rather than of instructions.

`PromptAssemblyTest` re-derives all 42 prompts and byte-compares them against
`app/src/test/resources/golden_prompts.jsonl`, which is generated by the Python side. It
also asserts the bundled assets are byte-identical to `../corpus.jsonl`, `../prompt.md`
and `../schema.json`. If that test is red, the Nano column is meaningless.

The three shared files are **copied in at build time** and gitignored here — the harness
dir is the only source of truth.

### Structured output is deliberately not used

The ML Kit Prompt API's structured-output path is alpha, is compile-time Kotlin
`@Generable` classes only, gives no guaranteed constrained decoding (it validates
post-hoc), cannot express this schema at all (no cross-field `items[0] == title`, no
"absent-or-`minItems: 2`", no enum-plus-optional-object nesting the way `label` needs),
and injects its own schema wording into the prompt — which would break the identical-
prompt invariant outright.

So the app runs plain `generateContent()` with the shared prompt, records the output
verbatim, and lets the same Python validator the hosted side uses classify it afterwards.
The hosted side was **not** weakened to match. That asymmetry is itself a bake-off
finding, and it is written up on #42.

Generation config: SDK defaults for sampling (temperature/topK/seed left unset — setting
them would be tuning a side the hosted parser never got), `maxOutputTokens = 256`,
`candidateCount = 1`. The full config is recorded in `nano_run_meta.json`.

**256 is a hard device ceiling, not a preference.** AICore rejects anything larger with
`IllegalArgumentException: maxOutputTokens must be between 1 and 256` — before any
inference, so every capture fails identically. The client SDK does not validate it; the
first phone run (2026-08-08) is how we found the number. It is still ~3x headroom: the
largest hosted parse is 265 characters, roughly 66-88 tokens. A response that is
nonetheless cut off is recorded as an honest failure, never repaired.

### Nano fences its output (observed 2026-08-08)

Every capture came back as well-formed JSON wrapped in ` ```json ` fences, despite the
shared prompt's "Output only JSON conforming to the schema. No prose, no code fences."
The hosted baseline never did this.

The prompt is **not** being tuned to fix it — identical wording on both sides is the
whole invariant, and changing it would invalidate the hosted column. The app still
records output verbatim. `merge_nano.py` unwraps an exact whole-output fence at
scoring time, counts it separately, and marks the cell `**FENCED:**`, so the envelope
failure and the parse quality stay two measurements rather than one. Prose outside the
fence is never unwrapped — that would be repairing content.

### Strict JSON, never lenient

Output is parsed with `kotlinx-serialization-json`, **not** `org.json`. Android's
`JSONTokener` is documented-lenient — single quotes, unquoted keys, trailing garbage —
and would launder malformed model output into a valid-looking parse before the Python
validator ever saw it. There is no trimming and no fence-stripping either: a fenced or
prose-wrapped answer is a recorded failure, and scoring gets to classify it.

### When a run is spoiled

Two guards exist because a recorded id is **never** re-run, which makes a bad run
expensive:

- A configuration fault (`EngineMisconfigured` — the SDK rejecting our request) aborts
  the run and records **nothing**. It would have failed identically on all 42 captures,
  and 42 identical error rows are indistinguishable from 42 model failures in the
  results file.
- Three consecutive **identical ENGINE errors** stop the run and leave the remaining
  captures unrun. That shape means a condition — quota, thermal, config — not a fact
  about any capture, and the untouched ids stay runnable later. Output the model *did*
  produce never trips this, however repetitive: "Nano fences every answer" is a finding,
  and one worth having for all 42 captures. The breaker guards the corpus against the
  phone, not against the model.

To throw a spoiled run away, use **Discard this run and start over** on the Done screen
(two taps, with a confirmation). Only for runs spoiled by something other than the model
— genuine model failures are results and belong in the file.

### Crash-safety

Every row is appended, flushed and `fd.sync()`ed before the next capture starts. On
relaunch the app skips every id already present (**including errored ones** — never
retried), truncates a torn final line away, repairs a complete-but-unterminated one, and
refuses to run at all if an unparseable line shows up anywhere else in the file.

## Build and test

```bash
export JAVA_HOME="/Applications/Android Studio.app/Contents/jbr/Contents/Home"
./gradlew :app:testDebugUnitTest    # golden byte-match + results-file + run-loop tests
./gradlew :app:assembleDebug        # -> app/build/outputs/apk/debug/app-debug.apk
```

Regenerate the golden prompts after any change to `../prompt.md`, `../schema.json` or
`../corpus.jsonl`:

```bash
cd .. && ./run_hosted.py --emit-prompts \
    --out nano-runner/app/src/test/resources/golden_prompts.jsonl
```

The Python-side merge script has its own tests in the repo suite:
`python3 -m unittest discover -s tests`.

### Dry run (debug builds only)

Exercises the whole pipeline with a fake engine — canned parses plus one
lenient-JSON output, one fenced output and one thrown exception — writing to
`dryrun_*.jsonl` so fake data can never be mistaken for a result:

```bash
adb shell am start -n net.twinion.nanorunner/.RunnerActivity --ez dryRun true
```

On an emulator the real mode will correctly report **Gemini Nano unavailable**: there is
no AICore there. Nano inference is only testable on the Pixel.
